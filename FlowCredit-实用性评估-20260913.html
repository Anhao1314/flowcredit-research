FlowCredit 实用性评估

评估日期 2026-09-13 · 对象：本地开发仓库 fc.v1（flowcredit-v2，External Alpha v0.1.1 / 引擎 v0.2.1 / intake v0.3.1）· 方法：逐文件读代码与文档后的产品级评审，非运行时压测
一句话总判断：工程工艺在黑客松出身的项目里属于顶尖水平，但作为「产品」，它现在交付的是一份高质量的证据问卷 + 一把未经校准的尺子。真正决定实用性的两环——证据独立核验与风险结果校准——尚不存在。今天它最成立的身份，是「人工复核前置的证据完备性检查器」，而不是能输出信用结论的评估产品。作为代码资产可给 A−，作为可售卖产品目前仍是 pre-MVP 骨架。

二、承诺的价值闭环，现在走到哪一环

已建1 · 证据填报与契约

intake v0.3.1 + Ajv 校验，LLM 仅可选抽取；手工填报

缺失2 · 证据独立核验

账单/遥测/银行等 6 类连接器一个都没有；verification 由申报方自己填

已建 · 扎实3 · 归一化与对账

Token 分桶 1% 对账、6 月连续序列校验、忽略申报方自带权重

部分4 · TAI / CCI 评分

规则真实可跑；权重与曲线专家拍定，对标 peer 中位数是模拟 fixture

刻意留空5 · PD / 额度 / EL

未校准，恒为 null；但前端 demo 仍展示 PD 2.3/85% 与 $20,000

已建6 · 复核结论与补证动作

decision band、missingInputs、确认事件 veto，输出克制

未开始7 · 真实用户回路

roadmap 漏斗停在「首个外部评估」之前；无复购、无补证重跑样本

环节 2 与环节 5 恰是信用风控产品的价值主体：前者决定「证据可不可信」，后者决定「分数能不能换成决策」。中间的 3、4、6 环做得再好，也无法替两端创造价值。

三、问题分级与替代方案

致命P1 · 价值闭环缺两环：核验靠自报标签、评分零校准
证据
rules-v021.js 中 6 个 sourceDomain 只是字符串集合，VERIFICATION_SCORES 直接采信调用方申报；PEER_PROFILES 全部 simulation:true，sampleSize 120 是 fixture 元数据；risk-core-v021.js 中 PD_pct / recommendedLimit / expectedLoss 恒为 null；中文进展说明 2.2 自己把「真实数据源接入」「PD 校准」列为高风险待验证，并称违约样本是「根本瓶颈」。
替代方案
不要按「评分产品」卖。v1 明确定位为 Evidence Readiness Screener（证据完备性筛查器）：买家不是放款方，而是愿意做人工终审的早期投资人、算力中介或 FA；产品输出「缺什么证据、哪里对不上、优先补什么」。
第一步
找 1 家真实 AI 算力/API 服务商，拿真实账单与发票跑一次 intake，逐字段标注「拿不到 / 拿得到但无法核验 / 可独立核验」——这张表就是连接器路线图的优先级依据。
致命P2 · 一句话定义在四种身份间漂移
证据
index.html 标题是「On-chain AI Credit Risk」；README 是「evidence-aware risk API」；进展说明是「Web3 与数字金融 AI 信用风控智能平台」；Finch 材料又是 Marketplace Agent。买家、场景、付费方均未锁定。
替代方案
收敛成一句任务定义，例如：「给需要判断 AI 算力/API 服务商可信度的人，10 分钟产出一份可追溯的证据缺口清单。」
第一步
把 README 首句、index.html title、进展说明定位、Finch LISTING 改成同一句；凡与这句无关的功能进 not-doing list。
重要I1 · Intake 对早期公司过重，最常见输出是「无法计算」
证据
24 个必填决策字段、6 个月连续月度序列，且 peer 必须同时匹配 modelTier/taskType/gpuModel，否则直接 critical 阻断（profilesFor()）。目标客户（早期 AI 企业）通常凑不齐，结果就是 not-computable / insufficient-evidence——诚实，但没有独立使用价值。
替代方案
定义 ≤8 个字段的「最小可评估包」（raw tokens、valid rate、GPU 小时、月度收入/算力支出、回款率），其余改为加分项；peer 缺失时降级为只输出 token 层原始指标（null 机制已具备，把 profile 缺失从 critical 改为降级即可）。
第一步
对 healthy/watch/sybil 三个固定案例做字段消融：逐个删字段，删掉任何不改变 decision band 的必填项。
重要I2 · Demo 与 API 口径分裂，且存在三条互相分歧的评分轨
证据
前端冻结基线展示 PD 2.3%/85%、授信 $20,000；API v0.2.1 刻意全部 null。另有 DeepSeek 裁决轨，CCI 与确定性轨不一致（795 vs 834/866，进展说明 1.5.1）。买家看完 demo 会以为产品能给授信结论；LLM 分数并列展示会稀释「确定性、可问责」这一唯一差异化卖点。
替代方案
前端 PD/额度永久标注 simulation calibration（或直接隐藏）；AI VERDICT 卡只展示证据抽取质量与解释，不再输出 LLM 打的 CCI/PD/额度。LLM 定位严格回到「抽取与解释，不得碰权威分数」——这条你们自己在 README 里已经写明，需要让 UI 也遵守。
第一步
报告页 PD/额度处加不可移除的模拟标记；view-ai.js 移除 LLM 分数区。
重要I3 · 分发零进展且在持续消耗维护成本
证据
Finch 提交包自 v0.1 起标注 Ready 但至今未提交；SUBMISSION.md 自己备注 Render 免费档冷启动与 Marketplace 要求冲突；roadmap 的「External Assessment #1 Passed（TAI 93.8/CCI 929）」对照 AGENTS.md 可知正是固定演练案例值，不是外部客户。
替代方案
给 Finch 提交设硬截止日期，或明确撤包；把「第一个外部评估」重新定义为非本人、用真实主体完成的评估。
第一步
两周内二选一：提交 Finch，或删除所有「ready/passed」类表述，停止维护这套材料。
打磨N1 · Peer 覆盖面过窄
证据与动作
仅有 H100-equivalent / mixed 两档 inference peer，其他画像直接 PEER_PROFILE_NOT_FOUND。补「无 peer 时输出原始指标 + 不打 physical/commercial 分」的降级路径，而不是报错阻断。
打磨N2 · 三套引擎版本并存
证据与动作
risk-core.js / -v02.js / -v021.js 与三份 normalize 并存，冻结纪律已在持续消耗精力。确认无外部调用方后删除旧版，别让「以后可能用」的兼容层继续累积。

四、今天就能用的，与不能声称的

现在就有实用价值

  • AI 企业尽调/证据打包清单：24 字段模型、分桶对账规则、自报证据 49 分上限，本身就是一份高质量 checklist，分析师今天就能拿去做材料质控。
  • 可复用的确定性评分骨架：版本化规则、缺数据给 null 而非凑分、veto 与评分分离、契约先行——真数据到位后不需要重构。
  • 试点敲门砖：67 个测试、Docker、鉴权/限流/幂等、JSON Schema 契约，工程卖相足以换来一次正式试点对话。
  • 架构参考：确定性引擎拥有权威输出、LLM 只做抽取解释的权责切分，设计正确且克制。

当前不能对外声称

  • 不能声称能预测违约或给出授信：PD/EL/额度恒 null 且无校准。
  • 不能声称证据已被核验：核验等级是申报标签，没有任何连接器。
  • 不能声称 peer 基准真实：全部是 simulation fixture。
  • 不能声称有客户或市场验证：0 外部用户、Finch 未提交、无重复调用。
  • 不能把前端 demo 的 PD/额度数字当成引擎输出。

五、90 天行动排序（按实用性杠杆，而非技术难度）

1

第 1–2 周 · 收口径：统一一句话定位；demo 与 API 口径对齐（I2）；Finch 提交或撤包（I3）。

2

第 3–6 周 · 见真人：用 1 个真实主体跑通「最小可评估包」，产出第一份真实证据缺口清单；据此做 intake 减法（I1）。

3

第 7–10 周 · 补一环：只做一个证据连接器——优先最可能拿到的 billing/API 用量或 GPU 遥测，而不是银行流水——把一个 sourceDomain 从「自报」变成「系统直取」。

4

第 11–12 周 · 攒样本：积累 10 个真实评估（即使没有违约标签），用人工复核结果回校 knot 曲线；但在拿到结果数据前，继续不输出 PD/额度。
